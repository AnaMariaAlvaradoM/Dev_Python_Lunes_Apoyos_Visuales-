Punto de partida

ARRANQUE — Pregunta de negocio

La seguridad comienza como una decisión de negocio: proteger personas, datos y operaciones.

Punto de aprendizaje

Decide antes de continuar


Pregunta guía

Imagina que construyes el backend de una biblioteca digital. Cualquier persona con la URL de tu API puede entrar a /usuarios y ver el nombre, el correo y el historial de préstamos de todos los usuarios. Y puede entrar a /usuarios/5 y hacer DELETE. ¿Es esto un problema técnico o un problema de negocio? ¿Qué pierde la biblioteca si esto pasa?


Punto de aprendizaje

Primera intuición


"Es un problema técnico, falta ponerle una clave a la API."


Los estudiantes suelen ver la seguridad como un candado que se agrega al final, un detalle técnico.


Punto de aprendizaje

Criterio técnico


Es ambos, y sobre todo es un problema de negocio.


Técnicamente falta control de acceso. Pero el daño es de negocio: se viola la privacidad de los usuarios, se expone información personal (correos, hábitos de lectura), cualquiera puede borrar cuentas ajenas, y la biblioteca queda expuesta legalmente por incumplir protección de datos.


Criterio técnico

La seguridad no es un candado que se pone al final. Es una decisión de arquitectura que define quién es quién y qué puede hacer cada quién. Eso es lo que aprenderemos hoy.

02
Riesgo real

EL PROBLEMA — Una API sin seguridad es una casa sin puertas

Toda API real debe identificar a quien llama y limitar lo que puede hacer.

Punto de aprendizaje

Por qué existe este tema?


Hasta ahora, todas nuestras APIs (Módulo 1 y 2) tenían una característica peligrosa que no habíamos nombrado:


Estaban completamente abiertas.


Cualquiera que conociera la URL podía crear, leer, editar y borrar datos. En clase eso estaba bien: estábamos aprendiendo a construir. Pero ninguna API real funciona así.


Punto de aprendizaje

El problema en dos preguntas


Toda aplicación seria debe responder dos preguntas antes de dejar pasar una petición:


  1. ¿Quién eres? → Autenticación
  2. ¿Qué tienes permitido hacer? → Autorización

Nuestra API de biblioteca no sabe responder ninguna de las dos. Hoy le enseñamos a responder ambas.

Modelo mental

MODELO MENTAL — La discoteca

La cédula, la manilla y las zonas permitidas conectan autenticación, token y autorización.

Autenticación

Confirma la identidad: el portero valida quién eres.

Token JWT

Transporta una credencial firmada entre peticiones.

Autorización

Decide qué acciones y datos corresponden a esa identidad.


Antes de cualquier definición técnica, construyamos la intuición.


Punto de aprendizaje

La escena


Piensa en una discoteca con seguridad en la puerta.


Verificación observable

Autenticación = el portero revisa tu cédula. Confirma que eres quien dices ser. Si tu cédula es válida, entras.


El token = la manilla que te ponen en la muñeca. Una vez validado, te dan una manilla. Ya no tienes que mostrar la cédula en cada puerta interna: basta enseñar la manilla.


Autorización = qué zonas te deja entrar la manilla. Una manilla normal entra a la pista. Una manilla VIP entra a la zona VIP. La misma manilla, distintos permisos.


Punto de aprendizaje

Por qué esta analogía importa


El token JWT es exactamente esa manilla: una credencial que llevas contigo y muestras en cada petición, para no tener que mandar usuario y contraseña cada vez.


Conserva esta imagen mental: conecta autenticación, token y autorización durante todo el proyecto.

Fundamentos

DEFINICIONES TÉCNICAS

Distingue identidad de permisos antes de escribir una sola línea de seguridad.

Punto de aprendizaje

Autenticación (Authentication)


Definición técnica. Proceso de verificar la identidad de quien hace una petición. Responde: ¿eres realmente quien dices ser?


Explicación sencilla. Es el portero revisando tu cédula.


Verificación observable

Aplicación profesional. El endpoint de login: recibe usuario y contraseña, y si coinciden con lo guardado, confirma la identidad.


Punto de aprendizaje

Autorización (Authorization)


Definición técnica. Proceso de determinar qué recursos y acciones tiene permitido un usuario ya autenticado. Responde: ¿qué puedes hacer?


Explicación sencilla. Es la manilla que define a qué zonas entras.


Aplicación profesional. Un endpoint que solo permite acceso a usuarios con rol admin. Ya sabemos quién es (autenticado), ahora revisamos si puede (autorizado).


Punto de aprendizaje

Diferencia clave (no confundir nunca)


PreguntaEjemplo
Autenticación¿Quién eres?Iniciar sesión
Autorización¿Qué puedes hacer?Solo admin borra usuarios

Primero autenticación, después autorización. Siempre en ese orden. No puedes revisar qué puede hacer alguien si todavía no sabes quién es.


Punto de aprendizaje

Decide antes de continuar


Pregunta guía

Si alguien está autenticado, ¿significa que puede hacer cualquier cosa en el sistema?


Primera intuición. "Sí, si ya inició sesión, ya tiene acceso."


Criterio técnico. No. Autenticado significa que sabemos quién es, pero no que pueda hacer todo. Un usuario normal inició sesión (está autenticado), pero no puede borrar a otros usuarios (no está autorizado para eso). Son dos capas independientes.

06
Token firmado

JWT — ¿Qué es y por qué se usa?

Comprende qué firma JWT, qué información expone y por qué debe expirar.

Header

Declara el algoritmo de firma.

Payload

Transporta identidad y expiración; se puede leer.

Signature

Detecta cualquier alteración del contenido.


Punto de aprendizaje

El problema que resuelve JWT


Ya validamos al usuario en el login. Pero HTTP tiene una característica incómoda: no recuerda nada entre una petición y la siguiente.


Cada petición llega "en blanco", como si fuera la primera vez. Entonces, ¿cómo sabe la API en la petición número 50 que ya iniciaste sesión en la número 1?


Punto de aprendizaje

Dos respuestas posibles


Opción antigua (sesiones en servidor). El servidor guarda en su memoria "el usuario 5 ya inició sesión". Problema: si tienes muchos servidores, cada uno tendría que recordarlo. No escala bien.


Opción moderna (JWT). El servidor no recuerda nada. En su lugar, le entrega al cliente una credencial firmada (el token). El cliente la manda en cada petición. El servidor solo verifica la firma. No necesita memoria. Escala perfecto.


Esta es la manilla de la discoteca: no hay una lista en la puerta, la prueba la llevas tú puesta.


Punto de aprendizaje

JWT — definición


Definición técnica. JWT (JSON Web Token) es un estándar para transmitir información entre dos partes de forma compacta y firmada digitalmente. La firma garantiza que nadie alteró el contenido.


Explicación sencilla. Es un carnet que lleva tu información y un sello imposible de falsificar. Cualquiera puede leerlo, pero nadie puede modificarlo sin romper el sello.


Aplicación profesional. Tras el login, la API genera un JWT con el id del usuario. El cliente lo guarda y lo envía en cada petición. La API verifica el sello y sabe quién eres sin volver a pedir contraseña.


Punto de aprendizaje

Anatomía de un JWT — las tres partes


Un JWT es un texto largo dividido en tres partes separadas por puntos:


LEER ESTRUCTURAtoken JWT
xxxxx.yyyyy.zzzzz

Cada parte tiene un nombre y una función:


1. Header (encabezado). Dice qué algoritmo se usó para firmar. Ejemplo: HS256.


Atención

2. Payload (carga). Los datos que transporta: el id del usuario, cuándo expira. Ojo: esto NO va encriptado, solo codificado. Cualquiera puede leerlo. Nunca metas una contraseña aquí.


3. Signature (firma). El sello de seguridad. Se calcula combinando header + payload + una clave secreta que solo el servidor conoce. Si alguien cambia una coma del payload, la firma deja de coincidir y el token se rechaza.


Punto de aprendizaje

Actividad práctica — inspeccionar un token real


Abre jwt.io (o un visor equivalente) y pega un token de ejemplo.


Observa en pantalla:


  • Que el payload se lee sin ninguna clave (por eso no se guardan secretos ahí).
  • Que si cambias una sola letra del payload, la firma se pone en rojo (inválida).

Esto ancla el concepto: el JWT no oculta información, garantiza que no fue alterada.


Punto de aprendizaje

Decide antes de continuar


Pregunta guía

Si el payload de un JWT se puede leer sin ninguna clave, ¿es seguro guardar ahí la contraseña del usuario "para tenerla a mano"?


Primera intuición. "Como el token está firmado y es seguro, sí se puede."


Atención

Criterio técnico. No, jamás. El payload está codificado, no encriptado: cualquiera que intercepte el token lo lee en segundos. La firma protege contra modificación, no contra lectura. En el payload solo va información no sensible: el id del usuario y la expiración. Nunca contraseñas ni datos privados.

07
Contraseñas

HASHING DE CONTRASEÑAS — Antes de tocar la base de datos

La contraseña nunca se guarda ni se recupera: se compara mediante un hash bcrypt.

Punto de aprendizaje

El problema


Criterio técnico

Vamos a guardar usuarios con contraseña. Primera decisión de ingeniería, y es crítica:


¿Guardamos la contraseña tal cual la escribió el usuario?


Atención

Nunca. Si alguien roba la base de datos, tendría todas las contraseñas en texto plano. Y como la gente repite contraseñas, comprometerías también sus correos y bancos.


Punto de aprendizaje

La solución — hashing


Definición técnica. Un hash es el resultado de aplicar una función matemática de una sola vía a un texto. De la contraseña sale el hash, pero del hash no se puede volver a la contraseña.


Explicación sencilla. Es como licuar una fruta: de la fruta sacas el jugo, pero del jugo no puedes reconstruir la fruta.


Atención

Aplicación profesional. Guardamos el hash, nunca la contraseña. Cuando el usuario inicia sesión, hasheamos lo que escribió y comparamos los dos hashes. Si coinciden, la contraseña es correcta, y nunca tuvimos que almacenar el original.


Punto de aprendizaje

bcrypt — la herramienta


Usaremos bcrypt, un algoritmo de hashing diseñado específicamente para contraseñas. Es lento a propósito: eso hace que un atacante que intente adivinar millones de contraseñas se demore una eternidad.


Lo manejaremos a través de passlib, una librería que nos da una interfaz limpia sobre bcrypt.


Punto de aprendizaje

Decide antes de continuar


Pregunta guía

Si guardamos solo el hash y no la contraseña, ¿cómo verificamos después que el usuario escribió la contraseña correcta al iniciar sesión?


Primera intuición. "Habría que desencriptar el hash para comparar."


Atención

Criterio técnico. No se puede desencriptar (es de una sola vía, es el punto). Lo que hacemos es: tomamos la contraseña que el usuario escribió ahora, le aplicamos el mismo hash, y comparamos ese hash nuevo con el que guardamos. Si son idénticos, la contraseña es correcta. Nunca reconstruimos el original.

Por qué fijamos bcrypt==4.0.1 (decisión de ingeniería, no capricho)


Diagnóstico

Las versiones nuevas de bcrypt (4.1 en adelante) cambiaron una parte interna que passlib necesita leer. El resultado es un error molesto al arrancar que dice, en resumen, que no puede leer la versión de bcrypt.

No rompe del todo, pero ensucia la consola y a veces falla el hash. Fijar bcrypt==4.0.1 es la combinación estable y probada con passlib. Lo dejamos escrito para que nadie tropiece con eso en clase ni en producción.


Diagnóstico

Cómo se lee el error si aparece. En la consola verás un mensaje sobre "error reading bcrypt version" y una referencia a un atributo __about__ que no existe. Si lo ves, es exactamente este problema de versiones.

Punto de aprendizaje

El archivo de conexión


📍 Archivo: app/database.py · Acción: crear desde cero.


CREAR DESDE CEROapp/database.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

DATABASE_URL = "postgresql+psycopg://postgres:TU_CLAVE@localhost:5432/biblioteca"

engine = create_engine(DATABASE_URL)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

Punto de aprendizaje

Explicación — repasemos cada pieza


  • DATABASE_URL — la dirección de la base. Formato: postgresql+psycopg://usuario:clave@host:puerto/nombre_base. Reemplaza TU_CLAVE por tu contraseña real de PostgreSQL.
  • create_engine — el motor, el traductor entre Python y PostgreSQL.
  • SessionLocal — la fábrica de sesiones. Cada petición abre una sesión para hablar con la base.
  • Base — la clase madre de la que heredarán todos nuestros modelos.
  • get_db — la dependencia que entrega una sesión y la cierra sola al terminar, gracias al yield y el finally.

Advertencia de la vida real (repaso Módulo 2). Si usas Copilot, revisa que no cambie la cadena de conexión por SQLite. A veces reemplaza esta línea por algo con sqlite:///. Si tu app de repente "funciona" pero no ves los datos en PostgreSQL, es esto.

Modelo de datos

MODELOS — Las tablas (repaso + rol de usuario)

Modela usuarios, libros y préstamos con relaciones y responsabilidades claras.


Punto de aprendizaje

Qué construiremos


Tres modelos: Usuario, Libro, Prestamo. Los modelos definen las tablas reales en PostgreSQL.


Repaso. Un modelo (SQLAlchemy) es la tabla. Un schema (Pydantic) es el contrato de la API. No son lo mismo y no se mezclan. El modelo vive en la base; el schema viaja por la red.


Punto de aprendizaje

Modelo Usuario


📍 Archivo: app/models/usuario.py · Acción: crear desde cero.


CREAR DESDE CEROapp/models/usuario.py
from sqlalchemy import Column, Integer, String
from sqlalchemy.orm import relationship
from app.database import Base

class Usuario(Base):
    __tablename__ = "usuarios"

    id = Column(Integer, primary_key=True, index=True)
    nombre = Column(String, nullable=False)
    email = Column(String, unique=True, nullable=False, index=True)
    password_hash = Column(String, nullable=False)
    rol = Column(String, nullable=False, default="usuario")

    prestamos = relationship("Prestamo", back_populates="usuario")

Punto de aprendizaje

Explicación — Usuario, campo por campo


  • __tablename__ = "usuarios" — nombre real de la tabla en PostgreSQL.
  • id — clave primaria, autonumérica, indexada.
  • nombre — texto obligatorio (nullable=False).
  • email — texto obligatorio y único (unique=True): dos usuarios no pueden tener el mismo correo. Indexado porque buscaremos por él en el login.
  • password_hash — aquí NO va la contraseña, va su hash. El nombre del campo lo deja claro a propósito.
  • rol — texto con valor por defecto "usuario". Este campo es la base de la autorización: distingue admin de usuario.
  • prestamos — la relación con la tabla de préstamos. Un usuario tiene muchos préstamos (1:N).

Decisión de diseño. ¿Por qué rol es un String y no una tabla aparte de roles? Porque hoy solo tenemos dos roles fijos. Un String es suficiente y simple. Si el sistema creciera a decenas de roles con permisos configurables, un junior lo dejaría así; un senior crearía una tabla roles. Hoy, para dos roles, la tabla sería sobre-ingeniería.

from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
from passlib.context import CryptContext

SECRET_KEY = "clave-secreta-de-la-biblioteca-cambiar-en-produccion"
ALGORITHM = "HS256"
MINUTOS_EXPIRACION_TOKEN = 60

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hashear_password(password: str) -> str:
    return pwd_context.hash(password)

def verificar_password(password_plano: str, password_hash: str) -> bool:
    return pwd_context.verify(password_plano, password_hash)

def crear_token(datos: dict) -> str:
    datos_a_codificar = datos.copy()
    expira = datetime.now(timezone.utc) + timedelta(minutes=MINUTOS_EXPIRACION_TOKEN)
    datos_a_codificar.update({"exp": expira})
    token = jwt.encode(datos_a_codificar, SECRET_KEY, algorithm=ALGORITHM)
    return token

def verificar_token(token: str):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        return payload
    except JWTError:
        return None

Punto de aprendizaje

Explicación — la configuración


  • SECRET_KEY — la clave secreta con la que se firman los tokens. Es el sello de la manilla. Quien la tenga, puede falsificar tokens. Por eso en producción va en una variable de entorno, nunca en el código.
  • ALGORITHM = "HS256" — el algoritmo de firma. Estándar y seguro para este caso.
  • MINUTOS_EXPIRACION_TOKEN = 60 — el token vale una hora. Después expira y hay que volver a iniciar sesión. Un token eterno es un riesgo: si lo roban, sirve para siempre.

Punto de aprendizaje

Explicación — el contexto de hashing


  • pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto") — configura passlib para usar bcrypt. deprecated="auto" deja que passlib maneje esquemas viejos si algún día migramos. Esta es la línea exacta que exige bcrypt==4.0.1 para no dar el error de versión.

Punto de aprendizaje

Explicación — hashear y verificar


  • hashear_password — recibe la contraseña en texto plano y devuelve su hash. Lo usaremos al registrar.
  • verificar_password — recibe la contraseña que el usuario escribió ahora y el hash guardado, y devuelve True o False. Lo usaremos al iniciar sesión. Observa: no desencripta nada, solo compara.

Punto de aprendizaje

Explicación — crear el token


crear_token construye la manilla:


  • datos.copy() — copiamos los datos para no modificar el original.
  • expira — calculamos el momento exacto de expiración: ahora + 60 minutos. Usamos timezone.utc para trabajar en hora universal y evitar líos de zona horaria.
  • datos_a_codificar.update({"exp": expira}) — agregamos la expiración. exp es un campo estándar del JWT que las librerías reconocen automáticamente.
  • jwt.encode(...) — firma y arma el token con la clave secreta.

Punto de aprendizaje

Explicación — verificar el token


verificar_token revisa la manilla:


  • jwt.decode(...) — verifica la firma y la expiración automáticamente. Si el token fue alterado o ya venció, lanza JWTError.
  • El try/except — si algo falla, devolvemos None en vez de reventar. Quien llame a esta función sabrá que None significa "token inválido".

Punto de aprendizaje

Decide antes de continuar


Pregunta guía

¿Por qué el token debe expirar? ¿No sería más cómodo para el usuario que durara para siempre?


Atención

Primera intuición. "Sí, así el usuario no tendría que volver a iniciar sesión nunca."


Criterio técnico. Más cómodo, pero peligroso. Si un token no expira y alguien lo roba (por ejemplo, de un computador público), tendría acceso para siempre. La expiración limita la ventana de daño: un token robado sirve máximo una hora. Es el equilibrio entre comodidad y seguridad, y en seguridad casi siempre gana la protección. Por eso existen los refresh tokens, que veremos más adelante.


Punto de aprendizaje

IA como copiloto — con criterio


Si le pides a la IA "genera la lógica de JWT para FastAPI", casi siempre te dará algo parecido a esto. Pero revisa siempre dos cosas:


  1. Que use datetime.now(timezone.utc) y no el datetime.utcnow() viejo (está en desuso).
  2. Que la SECRET_KEY no venga escrita como un valor real "de ejemplo" que luego se te olvide cambiar.

La IA escribe el patrón; tú garantizas que sea seguro. Ese es tu trabajo.

def registrar_usuario(db: Session, datos: UsuarioCreate) -> Usuario:
    existente = db.query(Usuario).filter(Usuario.email == datos.email).first()
    if existente:
        raise HTTPException(status_code=400, detail="El email ya está registrado")

    nuevo_usuario = Usuario(
        nombre=datos.nombre,
        email=datos.email,
        password_hash=hashear_password(datos.password),
        rol="usuario"
    )
    db.add(nuevo_usuario)
    db.commit()
    db.refresh(nuevo_usuario)
    return nuevo_usuario

def listar_usuarios(db: Session):
    return db.query(Usuario).all()

def obtener_usuario(db: Session, usuario_id: int) -> Usuario:
    usuario = db.query(Usuario).filter(Usuario.id == usuario_id).first()
    if not usuario:
        raise HTTPException(status_code=404, detail="Usuario no encontrado")
    return usuario

def eliminar_usuario(db: Session, usuario_id: int):
    usuario = obtener_usuario(db, usuario_id)
    db.delete(usuario)
    db.commit()
    return {"mensaje": "Usuario eliminado"}

Punto de aprendizaje

Explicación — registrar_usuario, el paso de seguridad


Esta función es donde la seguridad toca la base de datos.

La pieza que convierte un token en un usuario real. Es la que protege los endpoints: cualquier ruta que dependa de ella exigirá un token válido.

Punto de aprendizaje

El flujo que vamos a montar


  1. El cliente manda el token en el encabezado Authorization: Bearer <token>.
  2. FastAPI extrae el token automáticamente con OAuth2PasswordBearer.
  3. Nuestra dependencia verifica el token y busca al usuario en la base.
  4. Si todo va bien, el endpoint recibe el objeto Usuario listo para usar.

El archivo de dependencias

from fastapi import Depends, HTTPException
from fastapi.security import OAuth2PasswordBearer
from sqlalchemy.orm import Session
from app.database import get_db
from app.auth.seguridad import verificar_token
from app.models.usuario import Usuario

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="auth/login")

def obtener_usuario_actual(
    token: str = Depends(oauth2_scheme),
    db: Session = Depends(get_db)
) -> Usuario:
    payload = verificar_token(token)
    if payload is None:
        raise HTTPException(status_code=401, detail="Token inválido o expirado")

    usuario_id = payload.get("sub")
    if usuario_id is None:
        raise HTTPException(status_code=401, detail="Token sin identificación")

    usuario = db.query(Usuario).filter(Usuario.id == int(usuario_id)).first()
    if usuario is None:
        raise HTTPException(status_code=401, detail="Usuario no existe")

    return usuario

def requerir_admin(usuario: Usuario = Depends(obtener_usuario_actual)) -> Usuario:
    if usuario.rol != "admin":
        raise HTTPException(status_code=403, detail="Requiere permisos de administrador")
    return usuario

Punto de aprendizaje

Explicación — oauth2_scheme


OAuth2PasswordBearer(tokenUrl="auth/login") — esta línea hace dos cosas:


  • Le enseña a FastAPI a extraer el token del encabezado Authorization de cada petición.
  • Le dice a Swagger dónde está el login (auth/login), lo que activa el botón "Authorize" en la interfaz. Ese botón es lo que usaremos para probar.

Punto de aprendizaje

Explicación — obtener_usuario_actual, paso a paso


Esta es la dependencia estrella. La leemos con calma:


  • token: str = Depends(oauth2_scheme) — FastAPI saca el token del encabezado y nos lo entrega.
  • verificar_token(token) — reusamos la función de seguridad.py. Si el token es inválido o expiró, devuelve None.
  • Si es None → 401: "no sé quién eres".
  • payload.get("sub") — sub (subject) es el campo estándar del JWT donde guardamos el id del usuario. Lo sacamos.
  • Buscamos el usuario en la base por ese id.
  • Si todo está bien, devolvemos el objeto Usuario completo. El endpoint lo recibe listo.

Por qué es tan potente. Cualquier endpoint que escriba Depends(obtener_usuario_actual) queda protegido automáticamente. Sin token válido, ni siquiera entra a la lógica: FastAPI corta antes con 401.


Punto de aprendizaje

Explicación — requerir_admin, la autorización por rol


requerir_admin es autorización pura:


  • Depende de obtener_usuario_actual (primero autentica).
  • Luego revisa if usuario.rol != "admin". Si no es admin → 403.
  • Si es admin, lo deja pasar.

Esto encadena dependencias: para ser admin, primero hay que estar autenticado. FastAPI resuelve la cadena solo. Elegante y reutilizable.


Punto de aprendizaje

Decide antes de continuar


Pregunta guía

¿Por qué guardamos el id del usuario en el token (sub) y no su nombre o su email?


Primera intuición. "El email sería más fácil de leer y reconocer."


Atención

Criterio técnico. El id es la identidad estable e inmutable. El email o el nombre pueden cambiar; el id nunca. Si guardáramos el email en el token y el usuario lo cambia, el token viejo apuntaría a un dato desactualizado. Además, el id es más corto y no expone información personal en el payload (que recuerden, se puede leer). El id es la llave correcta.

from fastapi import APIRouter, Depends, HTTPException
from fastapi.security import OAuth2PasswordRequestForm
from sqlalchemy.orm import Session
from app.database import get_db
from app.schemas.usuario import UsuarioCreate, UsuarioRespuesta
from app.services.usuario_service import registrar_usuario
from app.models.usuario import Usuario
from app.auth.seguridad import verificar_password, crear_token

router = APIRouter(prefix="/auth", tags=["Autenticación"])

@router.post("/registro", response_model=UsuarioRespuesta)
def registro(datos: UsuarioCreate, db: Session = Depends(get_db)):
    return registrar_usuario(db, datos)

@router.post("/login")
def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    db: Session = Depends(get_db)
):
    usuario = db.query(Usuario).filter(Usuario.email == form_data.username).first()

    if not usuario or not verificar_password(form_data.password, usuario.password_hash):
        raise HTTPException(status_code=401, detail="Correo o contraseña incorrectos")

    token = crear_token({"sub": str(usuario.id)})
    return {"access_token": token, "token_type": "bearer"}

Punto de aprendizaje

Explicación — el registro


  • @router.post("/registro", response_model=UsuarioRespuesta) — recibe un UsuarioCreate, devuelve un UsuarioRespuesta. Por el response_model, FastAPI filtra la respuesta: aunque el objeto tenga password_hash, solo sale lo que define UsuarioRespuesta. La seguridad se aplica sola.
  • Delega todo al service. El router solo conecta; la lógica vive en el service (repaso de capas).

Punto de aprendizaje

Explicación — el login, la pieza clave


Este endpoint es el que entrega la manilla. Leámoslo con cuidado:


  • form_data: OAuth2PasswordRequestForm = Depends() — novedad importante. El login no recibe JSON, recibe un formulario. Es el estándar OAuth2. Por eso instalamos python-multipart. El formulario trae dos campos: username y password.
  • Ojo: OAuth2 llama username al campo de identidad, pero nosotros ahí mandamos el email. Es solo el nombre del campo del estándar.
  • Buscamos el usuario por email.
  • if not usuario or not verificar_password(...) — si el usuario no existe o la contraseña no coincide, error 401. Observa: el mismo mensaje para ambos casos. Es a propósito.
  • crear_token({"sub": str(usuario.id)}) — creamos el token con el id del usuario en sub. Convertimos a string porque sub debe ser texto.
  • Devolvemos access_token y token_type: "bearer". Ese formato es el que espera Swagger para el botón Authorize.

Decisión de seguridad — el mensaje ambiguo. ¿Por qué no decimos "el correo no existe" o "la contraseña es incorrecta" por separado? Porque le daríamos pistas a un atacante. Si dijéramos "el correo no existe", podría probar correos hasta encontrar cuáles están registrados. Un mensaje genérico no revela nada. Esto se llama evitar enumeración de usuarios.


Punto de aprendizaje

Decide antes de continuar


Pregunta guía

¿Por qué el mensaje de error del login dice "correo o contraseña incorrectos" en vez de precisar cuál de los dos falló?


Primera intuición. "Sería más útil para el usuario saber exactamente qué se equivocó."


Diagnóstico

Criterio técnico. Más útil para el usuario, pero también para un atacante. Si el sistema dijera "ese correo no existe", alguien podría probar miles de correos y armar una lista de cuáles sí están registrados (enumeración de usuarios). El mensaje ambiguo protege esa información. En seguridad, a veces una peor experiencia de usuario es el precio correcto de la protección.

Preguntas frecuentes


"¿El token se guarda en la base de datos?" No. El token vive en el cliente. El servidor no lo guarda: solo verifica su firma. Esa es la gracia de JWT (sin estado en el servidor).


"¿Puedo cerrar sesión / invalidar un token?" Con JWT puro, no directamente: el token vale hasta que expira. Invalidar antes requiere una lista negra (se menciona como tema avanzado en la próxima clase). Es una limitación real de JWT que conviene nombrar.


"¿Por qué el login usa username si yo mando el email?" Porque OAuth2PasswordRequestForm define ese campo con ese nombre por el estándar OAuth2. Nosotros decidimos meter el email ahí. Es solo la etiqueta del campo.


Atención

"¿Dónde debería ir la SECRET_KEY en un proyecto real?" En una variable de entorno (archivo .env), nunca en el código ni en Git. Lo veremos en la próxima clase. Hoy la dejamos en el código para no distraernos.


"¿Por qué separamos seguridad.py y dependencias.py?" seguridad.py son las herramientas puras (hashear, crear token). dependencias.py las conecta con FastAPI (extraer token de la petición, buscar usuario). Responsabilidades distintas, archivos distintos.


"¿bcrypt y JWT son lo mismo?" No, y es una confusión frecuente. bcrypt hashea contraseñas (para guardarlas seguras). JWT transporta la identidad después del login (la manilla). Uno protege el almacenamiento; el otro, la sesión.

IA como copiloto — criterio de validación


Buen momento para recordar al grupo: la IA genera el patrón de JWT en segundos, pero no decide que el rol se fije en el servidor, ni que el mensaje de login sea ambiguo, ni que el usuario_id salga del token. Esas son decisiones de ingeniería de seguridad. La IA escribe; el criterio lo pone el desarrollador. Esa es la diferencia entre copiar y entender.
