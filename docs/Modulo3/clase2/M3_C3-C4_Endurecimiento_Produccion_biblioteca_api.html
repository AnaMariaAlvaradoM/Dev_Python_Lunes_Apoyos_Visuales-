01 · Pregunta de negocio

Las llaves quedaron expuestas

La seguridad no falla únicamente cuando el algoritmo está mal; también falla cuando una decisión de configuración entrega el control del sistema.

Para pensar

Tu API de biblioteca funciona y la subes a GitHub. Dentro del código quedaron la SECRET_KEY y la contraseña de PostgreSQL. ¿Qué acaba de pasar y qué tan grave es?

Pista: piensa qué podría hacer otra persona si tuviera las mismas llaves con las que el servidor confía en ti.

Ver respuesta

Acabas de entregar las llaves del sistema.

La primera intuición suele ser “no pasa nada porque el repositorio es mío”. Sin embargo, un repositorio puede compartirse, clonarse, filtrarse o volverse público por error; además, existen bots que buscan secretos automáticamente.

Con la SECRET_KEY, un atacante puede firmar tokens falsos y hacerse pasar por cualquier usuario, incluso el administrador. Con la contraseña de la base de datos, puede intentar entrar directamente a la información.

!

Regla de producción

Los secretos nunca viven en el código. La solución comienza separando configuración y lógica antes de añadir más mecanismos.

Reconecta con la sesión anterior

El token actual vale una hora. Si expira mientras el usuario trabaja, ¿cómo mantienes la sesión cómoda sin convertir el token en una credencial eterna?

Hacer una sola credencial más larga también extiende el daño si alguien la roba.

Ver respuesta

Se necesitan dos tokens con funciones y duraciones diferentes.

Alargar el token parece cómodo, pero un token largo robado representa un riesgo largo. Un access token corto atiende las operaciones diarias y un refresh token largo solicita accesos nuevos.

Así se conserva una sesión cómoda sin ampliar innecesariamente la ventana de ataque de la credencial que viaja en cada petición.

03 · Problema real

Funcionar no es estar listo para producción

Tres debilidades separan una demostración local de un servicio que puede vivir frente a usuarios reales.

🗝️Secretos en el código

La firma JWT y la conexión a la base quedan visibles en archivos compartidos.

⏳Sesiones frágiles

El token dura una hora fija y expulsa al usuario cuando vence.

🚦Errores inconsistentes

Cada fallo de autenticación responde distinto y no sigue un contrato uniforme.

!

La diferencia crítica

Que algo funcione en tu computador no significa que esté listo para el mundo real.

Repositorios vigilados

Claves filtradas han provocado incidentes reales. Atacantes automatizados pueden encontrarlas en cuestión de horas y GitHub escanea secretos para alertar sobre exposiciones.

Netflix, Gmail y banca

El usuario casi nunca vuelve a iniciar sesión porque el acceso corto se renueva por detrás con una credencial de refresco más duradera.

El idioma de HTTP

Una banca no improvisa mensajes: responde con un 401 y un formato estándar que clientes distintos pueden interpretar.

3 frentes de endurecimiento

Configuración segura · sesión robusta · errores interoperables.

El objetivo es convertir una API que “funciona” en una API que un equipo profesional desplegaría con confianza. Cada debilidad se resuelve de forma incremental y verificable.

04 · Modelo mental

Una casa, dos credenciales y señales universales

Antes del código, construimos una intuición para decidir qué protege cada pieza y por qué existe.

🏠Secretos = llaves

05 · Tema 1

Sacar los secretos del código

La misma aplicación debe correr en desarrollo y producción con configuraciones diferentes, sin reescribir una sola línea.

Definición técnica

Una variable de entorno es configuración que vive fuera del código, en el sistema donde corre la aplicación. El programa la lee al arrancar.

Explicación sencilla

Es una nota que dejas por fuera: el programa la lee, pero la clave no queda escrita dentro de la puerta.

Aplicación profesional

Conexiones a bases, claves de pagos, correo y firmas se inyectan por entorno. El mismo código sirve en desarrollo y producción.

El archivo .env

Es un archivo de texto con pares CLAVE=valor para un entorno específico. Funciona como el bolsillo de las llaves y nunca se sube al control de versiones.

os.getenv() sin contrato

  • Todo llega como texto.
  • Un valor faltante puede fallar tarde.
  • El mensaje aparece lejos de la causa real.

pydantic-settings

  • Declara tipos y valores obligatorios.
  • Convierte la configuración.
  • Detiene la aplicación temprano y explica qué falta.

06 · Tema 2

La expiración es una decisión de ingeniería

La duración de un token define cuánto riesgo acepta el negocio y qué experiencia recibe el usuario.

15minutos de acceso
7días de refresco
2roles distintos

¿Qué significa que un token expire?

Al crear el JWT se incorpora exp, una fecha y hora exactas que viajan dentro del token firmado.

Cuando el servidor lo recibe, python-jose compara exp con la hora actual. Si ya pasó, jwt.decode lanza el error y el token se rechaza automáticamente.

Token muy largo · 30 días

  • El usuario casi nunca vuelve a iniciar sesión.
  • Si lo roban, el atacante conserva acceso durante 30 días.
  • La comodidad amplía la ventana de riesgo.

Token muy corto · 5 minutos

  • Una credencial robada deja de servir pronto.
  • Sin renovación, el usuario iniciaría sesión constantemente.
  • La seguridad aislada deteriora la experiencia.
Decisión de ingeniería

Si reducimos el access token a 15 minutos, ¿no empeoramos la experiencia al obligar al usuario a iniciar sesión cada 15 minutos?

La respuesta cambia cuando una segunda credencial puede renovar la primera sin repetir el login.

Ver respuesta

Solo sería molesto si el access token fuera la única credencial.

Cuando vence, la aplicación usa el refresh token —que dura días— para solicitar un access token nuevo automáticamente. El usuario no vuelve a escribir sus datos cada 15 minutos.

El diseño combina la seguridad de una exposición corta con la comodidad de una sesión larga.

i

Regla de la industria

La duración no es un número al azar. Responde al riesgo del negocio, a la frecuencia de uso de la credencial y a la experiencia que se desea sostener.

07 · Tema 3

El sistema de dos tokens

Acceso corto para reducir el daño; refresco largo para renovar la sesión sin pedir credenciales una y otra vez.

Flujo completo de renovación
1

Login

El usuario recibe access + refresh.

2

Trabajo

Envía access en cada petición.

3

Expira

A los 15 minutos recibe 401.

4

Renueva

Manda refresh a /auth/refresh.

5

Verifica

El servidor valida firma, fecha y tipo.

6

Continúa

Recibe un access nuevo sin notar el cambio.

Solo cuando el refresh token expira, a los siete días, el usuario vuelve a iniciar sesión de verdad.

Sin ella, un access token podría pedir refrescos o un refresh token podría abrir endpoints de datos. Cada credencial debe servir únicamente para su responsabilidad.

Construcción 1 de 2

Reemplaza seguridad.py por la versión consolidada

Este archivo integra la configuración del .env, conserva el hash de contraseñas y crea/verifica los dos tipos de token. Reemplaza todo el contenido existente.

Editar · reemplazar todobiblioteca_api/app/auth/seguridad.py
from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
from passlib.context import CryptContext
from app.config import settings

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hashear_password(password: str) -> str:
    return pwd_context.hash(password)

def verificar_password(password_plano: str, password_hash: str) -> bool:
    return pwd_context.verify(password_plano, password_hash)

def crear_access_token(datos: dict) -> str:
    datos_a_codificar = datos.copy()
    expira = datetime.now(timezone.utc) + timedelta(
        minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES
    )
    datos_a_codificar.update({"exp": expira, "tipo": "access"})
    return jwt.encode(datos_a_codificar, settings.SECRET_KEY, algorithm=settings.ALGORITHM)

def crear_refresh_token(datos: dict) -> str:
    datos_a_codificar = datos.copy()
    expira = datetime.now(timezone.utc) + timedelta(
        days=settings.REFRESH_TOKEN_EXPIRE_DAYS
    )
    datos_a_codificar.update({"exp": expira, "tipo": "refresh"})
    return jwt.encode(datos_a_codificar, settings.SECRET_KEY, algorithm=settings.ALGORITHM)

def verificar_token(token: str, tipo_esperado: str):
    try:
        payload = jwt.decode(token, settings.SECRET_KEY, algorithms=[settings.ALGORITHM])
        if payload.get("tipo") != tipo_esperado:
            return None
        return payload
    except JWTError:
        return None

Los secretos desaparecen del archivo

settings.SECRET_KEY, settings.ALGORITHM y las duraciones vienen de la configuración validada.

El acceso usa minutos

crear_access_token añade exp y la marca "tipo": "access".

El refresco usa días

crear_refresh_token comparte la estructura, pero cambia duración y marca.

La verificación exige contexto

tipo_esperado permite rechazar un JWT válido cuando se intenta usar en la puerta equivocada.

Construcción 2 de 2

Actualiza la dependencia que consume el token

Editar · versión finalbiblioteca_api/app/auth/dependencias.py
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from sqlalchemy.orm import Session
from app.database import get_db
from app.auth.seguridad import verificar_token
from app.models.usuario import Usuario

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="auth/login")

def obtener_usuario_actual(
    token: str = Depends(oauth2_scheme),
    db: Session = Depends(get_db)
) -> Usuario:
    credenciales_invalidas = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="No se pudo validar el token",
        headers={"WWW-Authenticate": "Bearer"},
    )

    payload = verificar_token(token, tipo_esperado="access")
    if payload is None:
        raise credenciales_invalidas

    usuario_id = payload.get("sub")
    if usuario_id is None:
        raise credenciales_invalidas

    usuario = db.query(Usuario).filter(Usuario.id == int(usuario_id)).first()
    if usuario is None:
        raise credenciales_invalidas

    return usuario

def requerir_admin(usuario: Usuario = Depends(obtener_usuario_actual)) -> Usuario:
    if usuario.rol != "admin":
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Requiere permisos de administrador"
        )
    return usuario
Tipo obligatorio

tipo_esperado="access" impide abrir datos con el token de refresco.

Un error coherente

La misma excepción cubre payload inválido, sub ausente y usuario inexistente. Reduce filtraciones y repetición.

HTTP profesional

WWW-Authenticate: Bearer comunica el esquema esperado y las constantes de status hacen el código legible.

Riesgo y función

¿Por qué el refresh token dura 7 días y no 15 minutos también, si una duración corta parece más segura?

Pregunta qué trabajo dejaría de cumplir si expirara al mismo tiempo que el access token.

Ver respuesta

Si ambos duraran lo mismo, el refresh token no evitaría ningún login.

Su trabajo exige una ventana mayor. Su seguridad proviene de que se usa poco, viaja solo a /auth/refresh y debe guardarse con más cuidado.

Seguridad no significa siempre “más corto”; significa diseñar la exposición correcta para la responsabilidad de cada pieza.

Editar · versión finalbiblioteca_api/app/routers/auth_router.py
from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm
from sqlalchemy.orm import Session
from app.database import get_db
from app.schemas.usuario import UsuarioCreate, UsuarioRespuesta
from app.schemas.token import TokenRefresh
from app.services.usuario_service import registrar_usuario
from app.models.usuario import Usuario
from app.auth.seguridad import (
    verificar_password,
    crear_access_token,
    crear_refresh_token,
    verificar_token,
)

router = APIRouter(prefix="/auth", tags=["Autenticación"])

@router.post("/registro", response_model=UsuarioRespuesta)
def registro(datos: UsuarioCreate, db: Session = Depends(get_db)):
    return registrar_usuario(db, datos)

@router.post("/login")
def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    db: Session = Depends(get_db)
):
    usuario = db.query(Usuario).filter(Usuario.email == form_data.username).first()

    if not usuario or not verificar_password(form_data.password, usuario.password_hash):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Correo o contraseña incorrectos",
            headers={"WWW-Authenticate": "Bearer"},
        )

    datos_token = {"sub": str(usuario.id)}
    access_token = crear_access_token(datos_token)
    refresh_token = crear_refresh_token(datos_token)

    return {
        "access_token": access_token,
        "refresh_token": refresh_token,
        "token_type": "bearer",
    }

@router.post("/refresh")
def refrescar(datos: TokenRefresh, db: Session = Depends(get_db)):
    payload = verificar_token(datos.refresh_token, tipo_esperado="refresh")

    if payload is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Refresh token inválido o expirado",
            headers={"WWW-Authenticate": "Bearer"},
        )

    usuario_id = payload.get("sub")
    usuario = db.query(Usuario).filter(Usuario.id == int(usuario_id)).first()
    if usuario is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Usuario no encontrado",
            headers={"WWW-Authenticate": "Bearer"},
        )

    nuevo_access = crear_access_token({"sub": str(usuario.id)})
    return {"access_token": nuevo_access, "token_type": "bearer"}
auth_router.pyDos puertas, una identidad
/registro

No cambia; continúa delegando en registrar_usuario.

/login

Verifica correo y clave; crea access + refresh con el mismo sub.

/refresh

Valida firma, expiración y tipo="refresh"; luego busca al usuario.

Errores 401

Incluyen WWW-Authenticate: Bearer y mensajes coherentes.

Cómo leer el login actualizado

Antes se creaba un solo token. Ahora crear_access_token y crear_refresh_token reciben el mismo sub —el id del usuario— y devuelven credenciales con duración y tipo diferentes.

El cliente usa el access para trabajar y reserva el refresh para renovar. El mensaje ambiguo de credenciales evita revelar si existe el correo, y el error adopta el header estándar.

Cómo leer /refresh

Recibe JSON mediante TokenRefresh. Si la firma, la fecha o el tipo fallan, devuelve 401. Si el usuario ya no existe, también rechaza la renovación.

Cuando todo es válido, crea únicamente un access token nuevo. El refresh se reutiliza hasta que expire.

Patrón de esta clase

  • El refresh se reutiliza durante 7 días.
  • No requiere guardar tokens en base de datos.
  • Es el patrón base adecuado para comprender el flujo.

Rotación avanzada

  • Cada uso entrega un refresh nuevo.
  • El anterior se invalida.
  • Exige persistencia y control de revocación.
La llave correcta

/auth/refresh no usa Depends(obtener_usuario_actual). ¿Es un error de seguridad dejarlo sin esa dependencia?

Recuerda en qué momento se llama este endpoint y cuál credencial ya dejó de ser válida.

Ver respuesta

No es un error: está protegido con una credencial diferente.

No puede exigir un access token válido porque se invoca justo cuando ese token expiró. Su protección consiste en verificar internamente un refresh token válido.

Aplicar la dependencia de access rompería la renovación. El criterio profesional es proteger cada puerta con la llave adecuada, no repetir la misma llave en todas.

Prueba 6 de 9 · Uso cruzado

Un access token no puede refrescar

Provoca el fallo correcto

En POST /auth/refresh, pega el access token dentro del campo refresh_token.

Debe responder 401: Refresh token inválido o expirado. El JWT tiene firma válida, pero su tipo es "access"; la marca evita usarlo en la puerta equivocada.

Prueba 7 de 9 · Uso cruzado inverso

Un refresh token no abre los datos

Provoca el fallo correcto

En “Authorize”, pega el refresh token e intenta GET /prestamos/mis-prestamos.

Debe responder 401: No se pudo validar el token. El refresh sirve únicamente en /refresh; no sustituye la credencial de acceso.

Prueba 8 de 9 · Contrato HTTP

El 401 comunica el esquema esperado

Lee los headers

Provoca un 401 —puedes reutilizar la Prueba 7— y revisa “Response headers” en Swagger.

Debe aparecer www-authenticate: Bearer. Ese header permite que cualquier cliente entienda qué autenticación exige el servidor.

Prueba 9 de 9 · Tiempo real

El access token expira y el refresh recupera la sesión

Con paciencia

Espera 15 minutos con un access token y vuelve a usarlo.

Versión rápida

Cambia temporalmente ACCESS_TOKEN_EXPIRE_MINUTES=1, reinicia, inicia sesión y espera un minuto.

El resultado debe ser un 401 por expiración. Después, la Prueba 5 debe entregar un token nuevo: acceso expira → refresh renueva → el usuario continúa.

10 · Entregable reutilizable

Checklist para cualquier API

Un control incompleto significa que la API todavía conserva una superficie de riesgo que debe resolverse.

API lista para producciónCinco frentes verificables
Contraseñas

Hash, privacidad y mensajes ambiguos.

Secretos

Fuera del código y documentados sin exponer.

Tokens

Duración, tipo y uso correcto.

Errores

401/403 consistentes y sin filtraciones.

Autorización

Rol y propiedad de los datos.

🔐Contraseñas
  • Nunca se guardan en texto plano; solo su hash con bcrypt.
  • El hash nunca sale en una respuesta de la API.
  • El mensaje de login es ambiguo: no revela si falló el correo o la clave.
🗝️Secretos y configuración
  • SECRET_KEY y contraseñas viven en .env, no en el código.
  • .env está en .gitignore y nunca se sube.
  • Existe un .env.example como plantilla para el equipo.
  • SECRET_KEY es larga y aleatoria, no una palabra adivinable.
🎟️Tokens
  • El access token es corto: dura minutos.
  • Existe un refresh token largo para renovar sin reloguear.
  • Cada token está marcado por tipo y se valida que se use en su lugar.
  • Todos los tokens expiran; ninguno es eterno.
🚦Errores y respuestas
  • Los fallos de autenticación devuelven 401 con WWW-Authenticate.
  • Se distingue 401 —no sé quién eres— de 403 —sé quién eres, pero no puedes hacer esto—.
  • Los mensajes no filtran información interna del sistema.
🛡️Autorización
  • Los endpoints sensibles verifican el rol.
  • Un usuario solo accede a sus propios datos.
  • El cliente no decide el rol; se asigna de forma controlada.
!

Regla final

Si un solo control queda pendiente, la API todavía no está lista para producción. Este checklist funciona como brújula para cualquier servicio que construyas.

!

La validación que detiene el arranque no es un bug

Es el contrato protegiendo la aplicación antes de que una configuración incompleta produzca un fallo más difícil de rastrear.

¿Se sube .env?

Nunca. Va en .gitignore. El repositorio comparte .env.example sin valores reales.

¿Por qué no os.getenv()?

Puede usarse, pero pydantic-settings tipa, valida y avisa al arrancar si falta un secreto.

¿Dónde guarda refresh el cliente?

En web, idealmente en una cookie HttpOnly. En móvil, en el almacenamiento seguro del sistema.

¿Se invalida antes de expirar?

Con JWT puro, no directamente. Necesitas una lista de revocación en base de datos o Redis.

¿Refresh debe ser JWT?

No necesariamente. También puede ser texto opaco y aleatorio guardado en base de datos. JWT es más simple para este escalón.

¿15 minutos es una regla fija?

No. 15–30 minutos es un rango común; banca y una app de notas aceptan riesgos distintos.

i

Trade-off de JWT

Invalidar inmediatamente exige guardar estado en el servidor. Ese control adicional sacrifica parte de la ventaja de una sesión JWT puramente stateless.
