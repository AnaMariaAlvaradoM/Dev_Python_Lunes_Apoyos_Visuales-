01CONTEXTO

🧭 Punto de partida

Punto de partida

¿Qué riesgo tendría una tienda si cada producto guardara su categoría como texto libre, sin conectarse con la tabla real de categorías?

La API ya puede crear y consultar productos, categorías y proveedores. Sin embargo, esas entidades todavía funcionan como islas: existen en la misma base, pero no se reconocen entre sí.

Caso de negocio

Tienda con datos que se contradicen

Un producto podría guardar tecnologia, otro Tecnología y otro una categoría inexistente. La aplicación tendría datos aparentemente válidos, pero imposibles de confiar.

Mapa del proyecto

La conexión administra la sesión; los modelos representan tablas; los schemas validan entrada y salida; los services ejecutan reglas y persistencia; los routers exponen las operaciones HTTP.

Comprobación inicial

Verifica una base sana

Antes de modificar la estructura, confirma que el proyecto puede levantarse y persistir datos.

    Ejecuta uvicorn app.main:app --reload desde la raíz tienda_dev.

  2. 02

    Abre http://127.0.0.1:8000/docs y revisa los endpoints existentes.

  3. 03

    Confirma en pgAdmin las tablas productos, categorias y proveedores.

  4. 04

    Crea y consulta una categoría de prueba.

Error frecuente

Qué ocurre: aparece ModuleNotFoundError: No module named 'app'.

Cómo leerlo: Python no encuentra el paquete raíz.

Cómo resolverlo: vuelve a la carpeta tienda_dev y ejecuta Uvicorn desde allí, no desde app/.

🔗 Modelo relacional

Definición técnica

Una foreign key es una columna que referencia la llave primaria de otra tabla y establece una restricción de integridad referencial.

En palabras sencillas

El producto no copia la categoría: guarda el identificador de una categoría que ya existe.

Ejemplo real

Es como usar el número de cédula para apuntar al registro de una persona, en lugar de reescribir todos sus datos en cada trámite.

Cardinalidad

Cómo imaginarlo

Una categoría puede agrupar muchos productos y un proveedor puede surtir muchos productos. Cada producto pertenece a una categoría y, opcionalmente, a un proveedor: dos relaciones uno a muchos.

REEMPLAZARapp/models/producto_model.py
from sqlalchemy import Column, Integer, String, Float, ForeignKey
from sqlalchemy.orm import relationship
from app.config.database import Base


class Producto(Base):
    __tablename__ = "productos"

    id = Column(Integer, primary_key=True, index=True)
    nombre = Column(String, nullable=False)
    precio = Column(Float, nullable=False)
    stock = Column(Integer, nullable=False)
    categoria_id = Column(Integer, ForeignKey("categorias.id"), nullable=False)
    proveedor_id = Column(Integer, ForeignKey("proveedores.id"), nullable=True)

    categoria = relationship("Categoria")
    proveedor = relationship("Proveedor")

Decisión de diseño

categoria_id es obligatoria porque todo producto debe clasificarse. proveedor_id permite NULL porque un producto puede registrarse antes de asignar proveedor.

MODIFICARapp/services/producto_service.py
from app.models.categoria_model import Categoria
from app.models.proveedor_model import Proveedor
from app.exceptions import CategoriaNoEncontrada, ProveedorNoEncontrado


def crear_producto(db: Session, datos: ProductoCreate):
    categoria = db.query(Categoria).filter(Categoria.id == datos.categoria_id).first()
    if categoria is None:
        raise CategoriaNoEncontrada(datos.categoria_id)

    if datos.proveedor_id is not None:
        proveedor = db.query(Proveedor).filter(Proveedor.id == datos.proveedor_id).first()
        if proveedor is None:
            raise ProveedorNoEncontrado(datos.proveedor_id)

    nuevo = Producto(
        nombre=datos.nombre,
        precio=datos.precio,
        stock=datos.stock,
        categoria_id=datos.categoria_id,
        proveedor_id=datos.proveedor_id,
    )
    db.add(nuevo)
    db.commit()
    db.refresh(nuevo)
    return nuevo

Dos niveles de protección

El service devuelve errores comprensibles antes de llegar a PostgreSQL. La llave foránea permanece como última barrera y protege la integridad incluso si otra ruta de escritura omite la validación.

def actualizar_producto(db: Session, producto_id: int, datos: ProductoCreate):
    producto = db.query(Producto).filter(Producto.id == producto_id).first()
    if producto is None:
        return None

    categoria = db.query(Categoria).filter(Categoria.id == datos.categoria_id).first()
    if categoria is None:
        raise CategoriaNoEncontrada(datos.categoria_id)

    if datos.proveedor_id is not None:
        proveedor = db.query(Proveedor).filter(Proveedor.id == datos.proveedor_id).first()
        if proveedor is None:
            raise ProveedorNoEncontrado(datos.proveedor_id)

    producto.nombre = datos.nombre
    producto.precio = datos.precio
    producto.stock = datos.stock
    producto.categoria_id = datos.categoria_id
    producto.proveedor_id = datos.proveedor_id
    db.commit()
    db.refresh(producto)
    return producto

from fastapi import HTTPException


@router.put("/productos/{producto_id}", response_model=ProductoRespuesta)
def actualizar(producto_id: int, datos: ProductoCreate, db: Session = Depends(get_db)):
    producto = producto_service.actualizar_producto(db, producto_id, datos)
    if producto is None:
        raise HTTPException(status_code=404, detail="Producto no encontrado")
    return producto

Antes de continuar

¿Por qué actualizar no necesita db.add()?
El producto ya fue consultado y la sesión de SQLAlchemy lo está siguiendo. Al cambiar sus atributos, la unidad de trabajo detecta las modificaciones; commit() las persiste. add() se necesita principalmente para incorporar un objeto nuevo.

Prueba verificable

Actualiza sin cambiar identidad

Ejecuta PUT /productos/{producto_id}, cambia precio y stock, y luego consulta el mismo id. El contenido debe cambiar, pero el identificador debe conservarse.

def eliminar(producto_id: int, db: Session = Depends(get_db)):
    eliminado = producto_service.eliminar_producto(db, producto_id)

    return {"mensaje": f"Producto {producto_id} eliminado"}

Respuesta coherente

El endpoint no usa ProductoRespuesta: después de borrar, el recurso ya no existe. Una confirmación describe mejor el resultado de la operación.

Antes de continuar

¿Qué demuestra recibir 404 al intentar borrar por segunda vez el mismo id?
Demuestra que la primera eliminación persistió y que el endpoint diferencia entre una operación realizada y un recurso inexistente. No se puede eliminar lo que ya no está.
